# Original transition stress A/B — preparation, not results

Manual standard macOS-14 / Xcode16.2 / iOS18.2 comparison; no user assets or device access. Both arms are built from the same workflow-driver commit and receive exactly the same original AVM2 fixture/UI test/fixture-source seed. Only `App/Player/PlayerSession.swift` differs: exact pre-guard `bfa826dd9b0b1fec306a3902bf8c28a941e2162a` vs guarded `c40afb47ccc6ad90642dc3422233c2d81eacb045`. Source SHA pins are checked before build, full production/test/fixture manifests are compared, and the new callback unit test is removed from BOTH trees because the exact baseline lacks its structured adapter. Runtime, render settings and build configuration remain identical.

One UI method imports the original fixture through the actual Files UI and performs exactly three trusted child transitions (initial generation0, then1..3), each mixed with portrait/landscape and actual Home/activate. Current scene, root boot identity and child counters must survive; explicit callbacks, not a screenshot alone, prove progress. No reload/restart recovery or retry-until-green is allowed. The tiny original fixture is not a size/performance proxy for a large private game.

The same simulator UDID is erased between sequential baseline/guarded arms, including all synthetic data. This is only an ephemeral hosted-runner simulator. Each arm has a15minute cap and test480second cap. Both arms run independently; either failure fails the overall comparison. Raw xcresults, screenshots/AX attachments, phase logs, crash reports, source/fixture hashes and xcodebuild exit status are retained7days. A startup failure is not classified as a transition failure; use phase markers and crash timestamps. Sequential host/order noise remains a limitation.

Prepare requires a frozen `fixture/` tree plus `fixture.lock.json` with `variant: "unload"` and exact `files` SHA256 mapping, and the isolated `TransitionStressUITests.swift`. Until those original fixture/UI sources are reviewed, this harness must not be published/dispatched as ready. Only normal unload is selected; unloadAndStop and upstream unload patches remain separate investigations. Three passing cycles would not prove a general crash fix, and failure of both arms would not implicate this native callback guard.

The final UI diagnostic inspection covers the complete retained native ring (at most60 entries), not all events since launch. Absence of a retained warning is not proof that no earlier transient context loss occurred. Fresh per-action boot/child/input counters and collected OS crash reports are independent evidence.

## Separately labeled iOS 18.5 diagnostic

`compare-transition-stress-ios18_5.yml` uses the standard macOS-15 runner, Xcode16.4 and an explicitly verified iOS18.5 simulator. It does not replace or reinterpret the failed iOS18.2 run. The original root fixture was corrected after Chrome exposed an invalid constant-pool operand; the corrected exact 13-file lock passed actual Chrome run40542253253 (four READY generations and three trusted transitions). The new lane pins that corrected lock and retains the same Session source comparison, strict state/Home assertions, time bounds and raw evidence. An alternate-OS pass would establish only this bounded synthetic diagnostic, not a phone crash fix. The historical iOS18.2 run did not reach any transition and also used the earlier invalid fixture; it is not a clean OS-only A/B comparison with this corrected lane.
